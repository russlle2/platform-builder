# Managed authentication email

`POST /api/auth/send-email` lets Supabase Auth use the app's existing protected Postmark connection. Supabase documents Send Email HTTP hooks as available on the Free plan. No new email account, SMTP credential recovery, or paid upgrade is required by this integration. A valid existing Postmark server token, verified sender, and available sending allowance are still required; configuration presence does not prove delivery.

The route remains disabled until `SUPABASE_AUTH_EMAIL_HOOK_ENABLED=true` and a fresh `SUPABASE_AUTH_EMAIL_HOOK_SECRET` are configured as secret, functions-only Netlify variables in the intended site's production context. Use 32 cryptographically random bytes encoded as `v1,whsec_<base64>`; never paste the key into chat, logs, or source control. The same value belongs in Supabase's Send Email hook secret. Up to two keys separated by `|` support an overlap rotation. Existing `POSTMARK_SERVER_TOKEN` and `EMAIL_FROM_ADDRESS` stay server-side.

The staging identity is fixed to `dailyclarity-staging.netlify.app` and project `yuviqftugmasjypkhrpo`. Production requires the exact `dailyclarity.org` / `psxmvaushwsboogfnyqi` identity **and** the separate `SUPABASE_AUTH_EMAIL_HOOK_SHARED_PROJECT_REVIEWED=true` sentinel. Production must remain disabled until the existing callback allowlist and shared email behavior have been reviewed. This review preserves permitted callbacks; it does not certify every website covered by a wildcard. Its recorded callback allowlist includes DailyClarity, HVAC, legal, dental, and single-label `*.netlify.app` hosts. The hook preserves an allowed callback's origin; it does not redirect another app's users to DailyClarity. Only `/auth/callback` with an optional safe `next` is accepted. The exact configured app base can become its canonical callback; the old `http://localhost:3000` default fails clearly.

Initial deployment and activation order (the hook is not yet enabled):

1. Verify the staging project/site identities. Generate a fresh key in memory and configure the new secret and route enable flag on that Netlify site. The Supabase hook itself must remain **disabled** at this point.
2. Keep Supabase unchanged and disabled, retaining the new key in the same process for the later signed probe and activation. CLI 2.120.0 omits URI and secrets when `enabled=false`; a disabled config push does **not** establish that they were stored. Prepare a minimal local config containing only `[auth.hook.send_email]` `enabled=true`, `uri`, and `secrets="env(SUPABASE_AUTH_EMAIL_HOOK_SECRET)"`. Use the normal supported CLI login to review `supabase config diff --project-ref <ref> --workdir <temporary-directory> --output-format json` in memory, requiring only these three declared properties. This is a **diff only**, with no push until step 4. Never print raw config output or save the key in plaintext.
3. Deploy the exact reviewed app release. Confirm its identity, then check that an unsigned hook request returns a JSON signature error. A correctly signed fixture with action `health_probe` must return the exact unsupported-type error; it sends no email. Do not put real OTPs or links into deployment logs. Retrieve the protected, read-only Postmark health report and require an authenticated Live server connection. Sender authorization and delivery remain unverified.
4. Only after those checks pass, recheck the published release and unchanged Auth settings, review the minimal three-field diff again, and push the key, URI, and `enabled=true` together. Read back only enabled state and URI. Preserve SMTP, email confirmations, other Auth settings, and callback consumers. Complete an actual magic-link request, inbox receipt, same-browser callback, and owned dashboard access. The prerequisite probes warmed this function: do not label this initial check a cold-start test. A later request after inactivity must record that the actual warm/cold state remains unknown. Only then consider production configuration after its separate shared-consumer review.
5. For rollback, disable only `auth.hook.send_email.enabled`, preserving all other settings. With custom SMTP disabled, this restores Supabase's restricted default email transport; it does not establish public customer delivery.

The endpoint authenticates the exact raw request with Standard Webhooks HMAC-SHA256 before parsing JSON, using constant-time digest comparison and a ±300-second timestamp window. It bounds the body to 64 KiB, pins verification links to the configured Supabase project, escapes HTML, ignores user metadata, disables provider tracking, and limits Postmark transport to 2.5 seconds. No provider errors, bodies, OTPs, hashes, or credential links are logged or returned. A successful response means Postmark accepted the email, not that the recipient received it. Retries can resend an email; there is no claim of distributed exactly-once delivery.

### Native Netlify execution and deadline regression

On Netlify, `netlify/functions/auth-send-email.ts` serves the same exact `/api/auth/send-email` URL using a small native function. The Next route remains a local and non-Netlify fallback. Both call the same synchronous handler, retain the same configuration and HMAC checks, and wait for Postmark acceptance before returning success. The exact hook path is excluded from Next middleware matching; similarly named paths remain covered. Privacy headers are set by the shared handler. No Supabase hook URI, signing key, provider credentials, or callback allowlist changes are needed. Runtime variables must remain available to Netlify Functions, rather than build-only scope.

The native response includes `X-DailyClarity-Auth-Handler: netlify-function-v1`. For a new release with the hook already configured, verify the exact deployment and runtime identity without invoking the hook. Make the first hook invocation a normal staged Auth signup or magic-link request, and verify the accepted Auth response, fresh inbox receipt, same-browser redemption, and authenticated dashboard. Only afterward check this marker on a GET request returning 405 with `Allow: POST`, then on an unsigned POST returning a signature error; neither probe sends email, but both can warm the function. If any hook probe already ran, use a later normal request after inactivity and explicitly record the warm/cold state as unknown. Do not infer a cold start merely from deployment or elapsed time.

The native route accepts all methods for dispatch, but its handler rejects every non-POST method before configuration or provider work. Netlify documents user-defined function configuration as taking precedence over framework-generated entries, and matching serverless functions before redirects; edge middleware executes earlier, which is why the exact matcher exclusion matters. Confirm the deployed route rather than inferring routing from a local Next response.

This change follows a real staging failure on 2026-10-16, using restored baseline `8965a762037fa171a67a19faa58c285451649bb8`. At 23:50:29 UTC, the normal Auth `/otp` request returned 422 with `Failed to reach hook within maximum time of 5.000000 seconds` after approximately 5.362 seconds. The resulting signup email reached the authorized inbox, but redeeming that original link in the same original browser profile after an explicit close and reopen at 23:52:38 UTC returned `One-time token not found`; the browser did not reach the dashboard. Receiving the message therefore did not establish a working sign-in. No private address, credential link, or token is needed in this record.

Supabase's five-second HTTP hook budget includes the entire request and retries. Framework initialization or a cold start is a plausible contributor, not an established cause of that incident. Moving the handler removes Next server and middleware initialization from the native hook path; local tests and packaging cannot prove the remote deadline is now met. Follow the first-invocation verification order above before accepting fresh release evidence. Retain timing, prior invocations, observed warm/cold uncertainty, and failure evidence truthfully. An unsigned probe or message delivery alone does not satisfy that gate; a warmed successful sign-in does not establish cold-start performance.

Signup, invitation, magic-link, recovery, email verification/change, reauthentication, and the documented security notification types are handled. Secure email change retains Supabase's asymmetric hash mapping; email-changed notifications go to the signed old address. Unknown action types fail explicitly. Supabase's current hook payload does not provide a separate previous recipient for identity-unlinked notifications, so those use its signed `user.email` field.
