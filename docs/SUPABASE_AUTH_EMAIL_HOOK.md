# Managed authentication email

`POST /api/auth/send-email` lets Supabase Auth use the app's existing protected Postmark connection. Supabase documents Send Email HTTP hooks as available on the Free plan. No new email account, SMTP credential recovery, or paid upgrade is required by this integration. A valid existing Postmark server token, verified sender, and available sending allowance are still required; configuration presence does not prove delivery.

The route remains disabled until `SUPABASE_AUTH_EMAIL_HOOK_ENABLED=true` and a fresh `SUPABASE_AUTH_EMAIL_HOOK_SECRET` are configured as secret, functions-only Netlify variables in the intended site's production context. Use 32 cryptographically random bytes encoded as `v1,whsec_<base64>`; never paste the key into chat, logs, or source control. The same value belongs in Supabase's Send Email hook secret. Up to two keys separated by `|` support an overlap rotation. Existing `POSTMARK_SERVER_TOKEN` and `EMAIL_FROM_ADDRESS` stay server-side.

The staging identity is fixed to `dailyclarity-staging.netlify.app` and project `yuviqftugmasjypkhrpo`. Production requires the exact `dailyclarity.org` / `psxmvaushwsboogfnyqi` identity **and** the separate `SUPABASE_AUTH_EMAIL_HOOK_SHARED_PROJECT_REVIEWED=true` sentinel. Production must remain disabled until all consumers of that shared Auth project are reviewed. Its recorded callback allowlist includes DailyClarity, HVAC, legal, dental, and single-label `*.netlify.app` hosts. The hook preserves an allowed callback's origin; it does not redirect another app's users to DailyClarity. Only `/auth/callback` with an optional safe `next` is accepted. The exact configured app base can become its canonical callback; the old `http://localhost:3000` default fails clearly.

Deployment and activation order:

1. Verify the staging project/site identities. Generate a fresh key in memory and configure the new secret and route enable flag on that Netlify site. The Supabase hook itself must remain **disabled** at this point.
2. The same key and URI may be prepared on staging Supabase with `enabled=false`. With the normal supported CLI login, use a minimal config containing only `[auth.hook.send_email]` `enabled`, `uri`, and `secrets="env(SUPABASE_AUTH_EMAIL_HOOK_SECRET)"`. Review `supabase config diff --project-ref <ref> --workdir <temporary-directory> --output-format json` in memory and require that only these three properties are declared before `config push`. Keep the key in the same process for the later signed probe; never print raw config output or save the key in plaintext.
3. Deploy the exact reviewed app release. Confirm its identity, then check that an unsigned hook request returns a JSON signature error. A correctly signed fixture with action `health_probe` must return the exact unsupported-type error; it sends no email. Do not put real OTPs or links into deployment logs. Retrieve the protected, read-only Postmark health report and require an authenticated Live server connection. Sender authorization and delivery remain unverified.
4. Only after those checks pass, change staging `auth.hook.send_email.enabled` to `true` with a minimal reviewed diff. Read back only enabled state and URI. Preserve SMTP, email confirmations, other Auth settings, and callback consumers. Complete an actual magic-link request, inbox receipt, same-browser callback, and owned dashboard access. Only then consider production configuration after its separate shared-consumer review.
5. For rollback, disable only `auth.hook.send_email.enabled`, preserving all other settings. With custom SMTP disabled, this restores Supabase's restricted default email transport; it does not establish public customer delivery.

The endpoint authenticates the exact raw request with Standard Webhooks HMAC-SHA256 before parsing JSON, using constant-time digest comparison and a ±300-second timestamp window. It bounds the body to 64 KiB, pins verification links to the configured Supabase project, escapes HTML, ignores user metadata, disables provider tracking, and limits Postmark transport to 2.5 seconds. No provider errors, bodies, OTPs, hashes, or credential links are logged or returned. A successful response means Postmark accepted the email, not that the recipient received it. Retries can resend an email; there is no claim of distributed exactly-once delivery.

Signup, invitation, magic-link, recovery, email verification/change, reauthentication, and the documented security notification types are handled. Secure email change retains Supabase's asymmetric hash mapping; email-changed notifications go to the signed old address. Unknown action types fail explicitly. Supabase's current hook payload does not provide a separate previous recipient for identity-unlinked notifications, so those use its signed `user.email` field.
